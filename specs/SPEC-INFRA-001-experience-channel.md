# SPEC-INFRA-001 · 体验版客户端与更新机制(开发永远不碰 owner 正在用的程序)

> 状态:Ready —— 真值 = specs/INDEX.md。
> 创建:2026-10-02;Pre-Draft 结论:owner 原话立项"专门起一个需求,根治这个问题……体验版上面有个更新按钮,平时置灰,有更新时高亮,一点更新就同步到最新版本"。
> 类型:基建(workflow §三,与业务 SPEC 平级,不占 Phase 号);反复的"新旧实例/点了没反应"假 bug 全部源于开发构建与 owner 客户端共用同一 exe,本 SPEC 根治。

## 〇、值不值得做

- 好处:owner 的客户端与我的一切构建/测试彻底解耦(零干扰);换版本从"我覆盖 exe+他猜要不要重启"变成"他点一个按钮";本会话已因共用 exe 产生 3 次疑似假 bug 的排查成本。
- 代价:约一天工程;新增一个本地更新目录与两个命令;**可能碰坏**:single-instance/data dir 按 identifier 分离后,旧会话数据需迁移。
- 判:值→做(owner 直接拍板)。

## 一、Pre-Draft 结论

- 核心选择题:无未决项——owner 已定交互(置灰/高亮/点击更新);实现路线按 §四决策表代取默认(A3)。
- 标杆对照:浏览器"检查更新"按钮(手动检查+重启应用);VS Code Insiders 自更新。
- **界面确认基线**:按钮位置=顶栏项目标签条右端常驻(§四 D4 代取,交付可视化验证)。

## 二、需求正文(R 编号;使用者视角)

| R# | 需求提要 |
|---|---|
| R1 | 体验版是独立安装的客户端(独立目录、独立数据、独立单实例),开发过程中的任何构建/测试/重启都不影响它运行 |
| R2 | 体验版顶栏有更新按钮:没有更新时置灰;有新版本时高亮提示,悬停可见更新说明 |
| R3 | 点击更新按钮:自动完成文件替换,提示重启,重启后即为新版本;更新失败有明确提示且原版本不受损 |
| R4 | owner 现有会话数据(项目、页签、设置)原样带入体验版,一次迁移 |
| R5 | 开发方"发布"动作 = 构建体验版并放入更新目录;owner 何时更新由他点按钮决定 |
| R6 | 更新按钮可手动刷新检查(点击置灰按钮=立即再查一次) |

**反例规则**:不做在线更新/更新服务器/签名体系(V1.5 §184 边界,本机制是纯本地文件同步);不自动重启(用户确认后才重启);更新源只认固定白名单目录(不接受任意路径);开发构建(仓库 target/ 下)永远不被体验版直接引用。

## 四、技术实现方案

### 结构

```
%LOCALAPPDATA%\AIProjectViewer\
├── app\ai-project-viewer.exe        ← 体验版本体(绿色单文件,快捷方式指向它)
└── updates\
    ├── ai-project-viewer.exe        ← 我构建后放的最新版(发布动作)
    └── update.json                  ← { "note": "本轮改了什么(给 owner 看)" }
```

### 关键机制

- **隔离**:体验版用独立 identifier `com.aiprojectviewer.app.exp`(构建期 `--config` 合并片段)——WebView2 数据目录、single-instance、state.json 位置全部按 identifier 分离,与开发版互不可见、互不激活。
- **版本判定**:文件内容 md5(流式)——updates 目录的 exe 与当前运行 exe 的 md5 不同=有更新(比时间戳稳,不受复制时间干扰);诊断面板已有的 Build 时间继续作为人眼对版本的凭据。
- **替换**(Windows 允许 rename 运行中的 exe):updates exe → 复制为 `app\ai-project-viewer.new` → 当前 exe rename 为 `.old` → `.new` rename 正名 → 提示重启;下次启动时清理残留 `.old`/`.new`。失败任一步即回滚提示,原版不动。
- **命令**:`check_update()`(读白名单目录,返回 {available, note})、`apply_update()`(上述替换流);前端顶栏按钮组件+启动时自动 check 一次(不轮询,内存/磁盘零驻留)。
- **迁移**(一次性,装机脚本完成):复制现有 `%APPDATA%\com.aiprojectviewer.app\state.json` → 新 identifier 的 config dir;建桌面快捷方式指向体验版。
- **发布脚本**(此后每轮交付):构建 experience 配置 → 复制 exe+写 update.json 到 updates 目录 → 通知 owner。

### 决策依据(后续翻案只翻这节)

| # | 结论 | 理由 | 当时排除了什么 | 为什么排除 |
|---|---|---|---|---|
| D1 | 体验版=独立 identifier 的绿色单文件,非安装包 | 与开发版全隔离的最小充分手段(数据/单实例/状态三处都按 identifier 分);免 NSIS 重装 | NSIS 静默安装 | 重;exe 自含资源无需安装器 |
| D2 | 更新判定=md5 内容对比 | 时间戳受复制行为干扰;内容级最真 | 版本号文件 | 版本号是人写的,md5 不会说谎 |
| D3 | 替换=rename 自更新三步法 | Windows 允许 rename 运行中 exe;经典可靠;无第三方 updater | tauri-plugin-updater | 面向在线发布/签名体系,本地单人场景过重(§184:updater OFF) |
| D4 | 按钮位置=顶栏右端常驻 | owner 说"体验版上面有个更新按钮"——顶栏最显眼;代取默认,交付可视化验证 | 放 Settings 面板 | 藏起来的更新按钮等于没有 |
| D5 | 启动时检查一次+手动刷新,不轮询 | 内存最小化原则(零驻留成本);本地目录检查无时效压力 | 后台轮询 | 违背内存原则且无收益 |
| D6 | 更新说明=update.json 的 note 字段(我每轮发布时写) | owner 悬停即知"这版改了什么",不用翻汇报 | 仅版本号 | 信息量不足 |
| D7 | 迁移只搬 state.json 一份 | 唯一有价值的旧数据(Phase 4 已集中);WebView2 缓存无迁移价值 | 全目录复制 | 缓存重建即可,搬了反而带旧账 |
