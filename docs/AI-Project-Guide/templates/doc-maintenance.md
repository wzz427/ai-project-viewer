# doc-maintenance —— 文档更新机制:改了 X,哪些文档必须跟着更新

> agent 做完一件事,靠记性想不全该更新哪些——本文 = 全量对照表。
> **什么时候用**:每次收口(一个功能做完 / SPEC 关账 / 一段工作交付)逐行扫一遍。

## 1. 底线三件套(每次进展都做)

1. **handoff.md**:顶部加日期+短描述("下一步从哪接"同步);
2. **changelog.md**(若已建):改了功能点必记、标 SPEC 号;纯重构/改文档可不记;
3. **git commit**:"做了什么+为什么",一个独立逻辑变更一次,带 pathspec。
   外加:**SPEC 状态一变 → INDEX.md 同步**(唯一台账)。

## 2. 同步总表(按改动类型路由;收口时逐行对照,命中几条做几条)

| 这次动了什么 | 必须同步 |
|---|---|
| **用户可见的产品行为** | spec.md 对应节(**最常被漏**——规格是"产品该是什么样"那本书,读的人会照它回头改) |
| **架构决策** | architecture.md §1 决策表 + §12 修订记录 |
| **目录结构**(加删移目录/模块职责变) | architecture.md §3 代码地图 |
| **开发环境**(解释器/命令/平台坑) | architecture.md §0 |
| **一个量出来的数 / 结论改口了** | 🔴 **grep 全仓逐处改**,原地留"某月某日改口,出处 X"——读的人会先撞上旧那句 |
| **踩了新坑** | lessons.md 加一条(独立 commit);高频的同步 quickref |
| **加/删/移 .md 文档** | docs/README.md(若有)一行账 + 双向断链自查;进 history 必登记 INDEX |
| 【项目自填:特有的联动,如"改提示词→重生成快照"】 | 【】 |

**收口自检一句**:"我这次动的每一类东西,**哪些文档承诺了跟现状一致?**逐行点名,不凭记性。"

## 3. 写/改任何文档之前(§5.0)

> **想象一个由新对话开启的、全新的 agent:它能不能在「需要的那一刻」
> (= 这条规矩被执行的那个时刻、那个场景)真的看到你写的东西?**

动笔前三问:① 这条规矩的触发条件是**具体动作**还是**判断题**?(判断题在心流里不会被问 =
大概率不执行)② 判断题能不能改写成绑在具体动作上、甚至让系统那一刻自动做掉?
③ 它放的位置是不是那个动作的必经之路?入口那句话跟 agent 会怎么开口问对得上吗?

## 4. 复述要守卫

凡是"在代码之外复述代码事实"的地方(承诺跟现状一致的清单、测试复刻的拼装顺序),
配一道**会红的静态断言**对拍。自检:"我写的这句是在复述某处事实吗?是 → 它漂了谁会红?
没人会红 = 现在就补断言。"(打日志不算守卫,没人看日志。)
