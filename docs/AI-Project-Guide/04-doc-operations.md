# 04 · 日常文档运营 —— 四本账、同步表、路由表、怎么汇报

> **答一个问题:需求在跑的同时,那些支撑性文档日常怎么维护、AI 最后怎么向 owner 汇报。**

---

## 一、四本账 + git log(谁写、答什么、怎么变短)

| 账 | 答什么 | 谁写 | 怎么变短 |
|---|---|---|---|
| `handoff.md` 交接页 | **上一段发生了什么、为什么这么改**、现在在哪 | 只有人(机器写不出"当初为什么") | **整批回收**:发一版把这批已完结的整批蒸馏进 `history/progress/` |
| `debts.md` 债务表 | **还剩什么没做、下一件动哪个** | 从源账汇总(项目小可手维护,漂了就上生成器) | 条目销账,自己就没了 |
| `changelog.md` | 每版对外改了啥(**第一次发版才建**) | 人 | 滚动归档:只留开发中+最近两版 |
| `lessons.md` | 哪些路别再走(症状+根因+修法+判据) | 人 | **只增不删**;靠 quickref 分流 |
| `git log` | 怎么一步步走到这里 | 人写提交说明 | 不需要 |

**最常混的一对(交接页 vs 债务表),动笔前判一句**:
"这句话去掉之后,**下一件动哪个**的答案会变吗?" 变 → 债务表,回源账改;
不变 → 叙事("为什么"),交接页。**交接页里永远不出现"还剩几件"的清单和数字。**

**债务表建起来之前,非 SPEC 的零散待办住哪**:handoff §三 **挂账区**——
它不只装"等 owner 的事";**债务表未建的阶段,它就是全部待办的家**(一行一件带去处:
建备份库、等 owner 拍的问题、没归入任何 SPEC 的小事)。待办散落、或明显超过约 10 条 →
该建 debts.md 了;建起后"我的待办"搬去债务表,§三 只剩"等 owner 的"。

**每段进展,当场四件**(跟 git add 一个性质,漏了这段活等于没发生):
① 动账(开/改/销,**只改源账那行的"去处"**)→ ② 交接页加一条(结论+下一步+去哪看全文)→
③ changelog 记功能点(标 SPEC 号;没发版前此步跳过)→ ④ commit(写"做了什么+为什么",
**必须带 pathspec**,不带会把别的会话暂存的文件替它交掉)。
**一件事的状态只住源账一处**——第二份是复述件,必漂,且单向漂(没人把"已修"改回"未修")。

## 二、doc-maintenance.md:改了 X,该更新哪些文档

新仓库模板:[`templates/doc-maintenance.md`](./templates/doc-maintenance.md)。两张东西别混:

1. **底线三件套**(每次进展都做):交接页 → changelog(若有)→ commit。
2. **同步总表**(按改动类型路由):收口时逐行对照。种子行:

| 这次动了什么 | 必须同步 |
|---|---|
| 用户可见的产品行为 | `spec.md` 对应节(**最常被漏**) |
| 架构决策 | `architecture.md` 决策表 + 修订记录 |
| 目录结构 | `architecture.md` 代码地图 |
| 一个量出来的数/结论改口了 | **grep 全仓逐处改**,原地留"某月某日改口,出处 X" |
| 开发环境(解释器/命令/平台坑) | `architecture.md` §0 |
| 踩了新坑 | `lessons.md` 加一条(独立 commit) |

**写/改任何文档之前先过一句话**:*想象一个由新对话开启的、全新的 agent——
它能不能在「需要的那一刻」(= 这条规矩被执行的那个时刻)真的看到你写的东西?*
判据不是"写得好不好",是"到那一刻它出不出来"。

## 三、doc-routes.md:规矩到点自动送达

**为什么需要它**:实测(源项目 32 个会话)——被入口表点名的文档命中率 **96%**,
没点名的 **32%**。"看到"是三件事:被想起(重灾区)/找得到/看到那一段。
再加一份"必读文档"救不了第一件——**"想起来去查表"本身就是要靠想的那一步**。

做法:路由表(模板:[`templates/doc-routes.md`](./templates/doc-routes.md))+ 平台钩子,
**动作发生那一刻自动把该看的那一节推到眼前**。三种抓手:
碰某个文件(路径通配)/ 敲某条命令(`$` 开头)/ owner 说某句话(`?` 开头,门槛最高)。

- 话前缀决定投递语义:(无)= 提醒一次 / **⏳** = 提醒+提交时再核一次(规矩当场做不完的) /
  **🚫** = 每次都拦(只给安全红线)。
- **加一条规矩 = 往表里加一行数据,机制一个字不改**——这是它不算"打补丁"、能一直活着的原因。
- 出处必须**精确到节**;指向整份文档等于没指。
- **加完一行,自己真触发一次**。
- 没有钩子基础设施之前,它退化为 AGENTS.md 路由表的扩容页(靠 agent 主动查——所以触发词
  必须写成 agent 会怎么开口问的原话)。

## 四、how-to-report.md:怎么向 owner 汇报

**为什么必须是"照着填的模板"而不是"汇报原则"**:源项目同一个毛病 owner 发过三次火、
规矩写过两遍,每次都是当天又犯——规矩是事后检查表,生不出正确的结构。
模板([`templates/how-to-report.md`](./templates/how-to-report.md))要点:

1. **节标题 = owner 会问的那句话,不是你的发现的名字**(这条是灵魂:把排序权从写的人手上
   拿走,交给读者的认知顺序)。❌"一个值得注意的发现" ✅"为什么会这样?"
2. **第一句就是结论**;先打比方再给事实;一条消息只讲一件事(数"要他拿主意的事"有几个,>1 就拆)。
3. **进度汇报第一句固定三数**(有债务表后):"还欠 N 笔,其中 M 笔随下次发版消掉——
   要清零的是差 N−M=G 笔。" 三个数各有各的活,缺一个他就读不出进度。
4. **收尾必须是表**:做什么 · 多久 · 要不要你点头。没有这张表 = 没交付。
5. **禁词**:内部编号(SPEC-077/B36)一个不许出现;工程黑话先翻译
   ("探针"→"平台自动帮他试跑");自检:*这条消息里每个专有名词,拿掉之后他还看得懂吗?*
6. **每次被打回,当天往"他追问了什么→哪格没填够"对照表加一行**——追问是读数,不是噪音。

## 五、changelog 的时机(再强调一次)

**第一次要发版时才建。** 之前功能变化记在交接页和 SPEC 里就够;
建早了就是一份没有读者的空转账(owner 亲手删过一份)。
发版节奏定了之后:改功能点必记、标 SPEC 号、只留"开发中+最近两版"、更早的滚进 `history/releases/`。
