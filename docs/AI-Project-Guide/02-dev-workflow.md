# 02 · 需求驱动开发 —— 拆解、specs/ 逐个过、每个需求的三步曲

> **答一个问题:一个需求从 owner 的一句话到交付,怎么走。** 这是项目的日常主干。
> 流程文档落在新仓库的 `docs/workflow.md`(模板:[`templates/workflow.md`](./templates/workflow.md)),
> 本文讲怎么用、每步的判据。

---

## 全流程一张图

```
总需求(demand.txt) ─讨论→ spec.md + architecture.md     〔01-startup,已完成〕
        │
        ▼ 拆解
   roadmap.md(分批/依赖/验收)
        │
        ▼ 建立
   specs/ 文件夹 + INDEX.md 台账
        │
        ▼ 逐个需求(specs/SPEC-NNN),每个都走三步曲:
   ┌─────────────────────────────────────────────┐
   │ (a) 讨论:思路 + 技术方案;要界面的先确认界面   │
   │ (b) 落笔:技术实现方案写进 SPEC → 再开发        │
   │ (c) 交付:自测 → 测试用例 → 可视化验证 → 交 owner│
   └─────────────────────────────────────────────┘
```

## 一、拆解:roadmap.md

spec.md 定稿后,把功能清单拆成**批次**(第一批做什么、依赖谁):

- 每批 = 一组能一起交付的 SPEC 号 + **这批的验收标准**(用使用者视角描述,不是技术术语);
- 依赖顺序写明(什么必须先做);**第一批永远是最小可跑通的那条主路径**,别先做边角;
- roadmap 是活文档:批次做完的标 Done,新需求插队进来也记在这——**它是"接下来做什么"的顶层视图**,
  更细的待办去债务表([`04-doc-operations.md`](./04-doc-operations.md)),两层别混。

## 二、specs/ 文件夹与台账

- `specs/INDEX.md` = 唯一台账:每个 SPEC 一行——**编号 | 标题 | 状态(Draft/Ready/InDev/InTest/Done/已作废)| 去处(下一动作·归谁·什么时候)**。
- **每笔必须有"去处"**,没有去处的条目不许存在(那就是埋坑)。
- **未立项的功能不占号**:spec.md 功能清单对未立项的标"(规划中,见 roadmap)",
  立项(建 SPEC 文件)那天才给号——占号后拆解变卦会留死号。
- 编号只增不复用;**作废的 SPEC 不删,重标注**(写清"作废了以及为什么"——
  旧设计的身份不是理由,它的理由才是理由)。

## 三、每个需求的三步曲(核心中的核心)

### (a) 先讨论,后动笔 —— 思路和技术方案;界面先行

**写 SPEC 文件之前的硬门槛是"讨论过了",没讨论不许写**(owner 原话教训:
直接甩 200 行需求文档 = 把梳理需求的活推给他)。讨论三件:

1. **这件事值得做吗**(30 秒):好处(谁受影响·多大比例·**用数**)/ 代价(时间·机时·
   **它可能碰坏什么**←最常漏)。三出口:值→做;不值→判定不做、写清凭什么;
   值但不值得单独付→并进一件本来就要付的事。
2. **核心选择题 3-5 个**(每个 2-3 选项、带取舍、标推荐):判别法——
   "这个问题答 A vs B,SPEC 内容会差超过 30% 吗?" 是→问;否→取默认。
   有行业标杆 → 至少一题"跟谁一样 vs 不一样在哪"。
3. **涉及界面的,界面方案先行**:线框/布局草图/参考截图放进 SPEC。owner 在场 → 当场点头
   "就是这个"才算确认;**不在场 → 代取默认并在 SPEC 标"未确认"**(代拍规矩见 §六)。
   门槛统一为:**界面未获 owner 确认,不许进 InDev**(不是"不许写 SPEC"——线框随 Draft 出,
   确认卡在 Ready→InDev 那道门上)。**没确认就开发 = 返工概率最高的那一种。**

### (b) 确认清楚后,设计技术实现方案 → 再开发

讨论结论落进 SPEC(模板:[`templates/SPEC-template.md`](./templates/SPEC-template.md)),
其中两个节不能省:

- **需求正文(R 编号 + V 编号)**——写法见下面第四节;
- **技术实现方案**:模块怎么拆、动哪些文件、关键取舍;**决策依据节**记
  "结论 + 理由 + 当时排除了什么 + 为什么排除"——三个月后有人想推翻,翻的是这一节。
  **同一条依据同步写进它管的那段代码的头注释**(依据和它管的东西不许分家)。

状态机推进(每档跃迁有自检,全文住新仓库的 `docs/workflow.md`):

```
Draft(写正文)→ Ready(测试覆盖矩阵已出、方案 owner 拍过)
→ InDev(开发)→ InTest(自测全绿+可视化验证过,交 owner)
→ Done(owner 验收原话落进 SPEC)→ 冷却后归档进 specs/archive/
```

### (c) 代码生成后:自测 → 测试用例 → 可视化验证 → 交付

**顺序不许乱,少一步不许交**(细则在 [`03-testing.md`](./03-testing.md)):

1. **自己先跑起来**:功能真的能用(冒烟);**给 owner 验收前备好"双击就能跑"的启动物**,
   不让他拼命令、设环境变量;
2. **写测试用例**:从 SPEC 里的 **V 验证标准**逐条转化(见 03);R↔V↔用例对得上;
3. **可视化验证**:界面/行为改动 → **截图或录屏,自己打开看过**;
   "成功态跟没发生长得一样"的功能,还要配"怎么造出那个时刻+怎么看出它发生了"的读数办法;
4. **交付**:按 how-to-report 汇报;owner 验收原话记进 SPEC,状态改 Done。

## 四、需求文档(SPEC)的写法 —— 编号、使用者视角、验证标准

> 这是从源项目提炼的硬规矩:**需求文档写得糊,后面测试用例和验收全是空中楼阁。**

### 三要素缺一不可

1. **编号**:需求条目 R1、R2……;**验证标准 V1、V2……**(R 和 V 分开编号、互相引用)。
   编号是回溯的锚——测试、代码注释、汇报都按号引用,没有号就无处指。
2. **站在使用者视角写清流程**:每条 R 写"用户在什么场景 → 做什么操作 → 看到什么/发生什么",
   **不写实现**("点击保存按钮,右上角出现'已保存'提示" ✓;"调用 save API 更新 state" ✗)。
   使用流程按"一个用户从头走一遍"的顺序写,像说明书,不像功能罗列。
3. **验证标准(V)写清楚**:每条 R 至少配一条 V,**可判定**——"什么样算对"要写得能直接变测试用例:
   ✓ "输入空名字点创建,弹窗不关、名字输入框变红、提示'名称不能为空'"
   ✗ "有合理的输入校验"(什么叫合理?没法验)
   人工才能感知的(视觉调性)显式标 V-human,但原则上不超过自动项的一半——超了说明可测性差,先改设计。
   **计数口径:一条 V 只算一边,按主判定动作归**——机器断言能判的算自动,需人看画面的算人工。

### 穷尽性自检(推 Ready 前过一遍)

- **"看似一个按钮"警觉**:SPEC 简单到只有 3-5 条规则描述一个 UI 元素 → 大概率漏。
  任何"X 按钮/抽屉/弹窗"实际至少含:空态/加载/错误/重名/快捷键/撤销/持久化……
  两个工具:①"开源产品的话,用户会提多少 feature request?每条都是潜在 R";
  ②"成熟工具怎么处理这类场景?"照搬合理的+拍掉不合理的。
- 维度清单:触发器穷尽 / 状态穷尽(空·满·加载·错误·首用)/ 边界事件(切换·重启·取消·
  重复触发·并发·失败)/ 跨场景一致性 / **反例规则明示**(不许做什么)/ 持久化边界 / 撤销与副作用。
  **不适用的维度显式标 N/A + 一行理由,不许默默跳过**(跳过的事后看不出"想过没有")。
- **测试覆盖矩阵**(Draft→Ready 的硬产物):每行 R# / V# / 测法(自动|人工) / 所需夹具 / 状态(✓/⚠+方案)。
  **游离 R(没 V 的)不许存在**;缺口大的先开基建类需求补,别硬写。

## 五、owner 不在场时怎么办(代拍规矩)

> owner 异步/缺席是常态(深夜、出差、他就是没回)。整套流程默认他在场;缺席时按五条降级,
> **红线只有一条:不许编造"owner 已同意"**:

1. **只有明文预授权的才可代拍**:需求原话/已有决策里写着"你定 / 先做最简单的"→ 可代取默认;
   没有明文授权的产品方向、花钱、对外 → 挂起等他,不许代拍。
2. **代取的一切必须明标**:SPEC 里写"代取默认/未确认",并把本要问的问题汇成清单挂 handoff §三。
3. **跃迁照走、证据照留**:状态机不停摆,但跃迁记录写明代拍依据 + **回退条件**
   (他复核有异议 → 回哪一步)。
4. **不可代拍的硬门**:InTest→Done(owner 验收原话)、对外发布、**未确认的界面线框不许进 InDev**。
5. owner 回场后**逐条复核**挂账区,结论当天写回对应 SPEC/决策表——
   代拍买的是"不停摆",不是"已拍板"。

## 六、两个配套规矩

- **基建类需求(SPEC-INFRA)是一等公民**:当某个验证手段被反复需要
  (trace 通道、回放器、测试夹具、基准),单开 INFRA 编号系列做——
  **项目复杂到一定程度,验证平台本身就该立项开发**,别每个需求现造测试装置。
- **改公共的东西绝不补丁式**:改所有场景共用的代码/规则,自检
  "换一个完全不同的项目还成立吗?"——措辞里冒出当前项目专有名词 = 八成是补丁。
