# 03 · 验证与测试 —— 怎么证明"做对了"

> **答一个问题:代码写完了,交付之前怎么验证。** 对应三步曲的第 (c) 步。
> 落到新仓库是 `docs/testing.md`(模板:[`templates/testing.md`](./templates/testing.md))。

---

## 一、总纲:验证标准是测试之母

**测试用例不是写代码时现想的,是从 SPEC 的 V 验证标准逐条转化来的。**
SPEC 里没有 V → 测试无从写起 → 回 [`02-dev-workflow.md`](./02-dev-workflow.md) §四补 V,别硬编用例。
转化关系:一条 V 至少一个用例;用例的断言就是 V 写的"什么样算对",一字不差。

## 二、自测三层(顺序:先跑通,再自动化,再看画面)

| 层 | 干什么 | 判据 |
|---|---|---|
| 1 冒烟 | 自己把功能**真跑起来用一遍** | 主路径走得通;给 owner 验收前备好**双击就能跑**的启动物 |
| 2 测试用例 | 把 V 变成自动化用例(单测/组件/E2E,按项目栈) | R↔V↔用例对得上;断言=V 原文;"成功态跟没发生长得一样"的功能,还要造出那个时刻并断言它发生了 |
| 3 **可视化验证** | 界面/行为改动 → **截图或录屏,自己打开看过** | 🚫 没看过的图不许入库、不许凭它说"验证过了"——机器证明得了"图存在",证明不了"画面对不对" |

**可视化验证为什么单列一层**:文字断言只覆盖"已经想过的那一种歪法",
每次真出事的画面当时都不在断言表上。所以 UI 类交付的最后一格永远是**人眼看画面**。

## 三、测试什么时候跑(挂动作,不挂时钟)

**时钟不知道你改没改东西,动作知道。** 定时全量 = 替一道没建起来的闸打工。

| 什么时候 | 跑什么 | 谁说了算 |
|---|---|---|
| 动完代码 | 静态闸(typecheck/lint,秒级) | 自己拍,照跑 |
| 要 commit | **只跑跟这次改动直接相关的一小份**(那个 spec 文件/那个模块) | 自己拍 |
| 改了用户看得见的东西 | 一张截图自己看过再 commit | 自己拍 |
| 全量/整套 E2E | —— | 🔴 **owner 批准,一次一议**;节奏=修完一批→申请一次(批没修完就跑,指纹一动全作废) |
| 发版 | 发版闸(硬卡,红一道不许打) | 发版本身已要 owner 点头 |

## 四、测试跑挂了,怎么找根因(科学家帽速查)

1. **先分类**:代码逻辑错 / 环境问题 / 测试装置自己不真实——**测试红了先分"产品坏了"还是"装置假了"**。
2. **复现不出 = 没理解,不动代码**:两次没复现就是没复现,绝不归"偶发";
   必要时上最末端 trace(日志/字节流),别只看聚合结果。
3. **改一行好了 ≠ 根因对了**:回归对照——改前现象稳定出现、改后稳定消失,两组都稳才算修对。
4. **别人报的 bug:现象多半是真的,结论不一定**:先认现象 → 翻自己的判据(V/规格)→
   再拿数据数;别照报告人的结论直接改。
5. 统计边界:事件数不到两位数 → 别做统计,去查机理(哪个进程/哪条链路)。

## 五、守卫与发版闸(随项目长大)

- **复述必守卫**:凡是"文档/测试里复述了代码事实"的地方(承诺跟现状一致的清单、
  复刻的拼装顺序),配一道**会红的静态断言**对拍——不报错的漂移比错误更贵。
  守卫自检两招:① 期望值**独立写死**,不许从被守对象里取(取了=假守卫,东西改小、用例跟着消失、全绿);
  ② 写完守卫**坏件回跑**一次:改回出事前的样子,它必须当场红。
- **发版闸(第一次打包前建)**,每道闸只答一个问题,先过两问再加:
  ① **拿上一次事故回测,它会不会红?** 答不出"会"= 仪式,别加;
  ② 它看的东西跟用户屏幕上的,**隔着几层?**(自己造输入→自己写断言 = 隔三层,核对自己的世界观)。
- **灰度→正式转正总表**:灰度包上架当天建一份"转正式前必须过完"的清单
  (owner 实测问题/等下个包的改动/正式版才铺的配套/剩余验收/转正当天动作——这五类天生散在五处,
  没这张表转正全靠记性),正式发出后整体归档。
