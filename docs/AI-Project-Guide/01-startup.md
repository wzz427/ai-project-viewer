# 01 · 启动项目 —— 第一天干什么,总需求怎么讨论

> **答两个问题**:① 仓库刚建好,第一天按什么顺序做什么;② 总需求讨论怎么做、
> 产出什么。做完这份,项目就进入 [`02-dev-workflow.md`](./02-dev-workflow.md) 的节奏。

---

## 一、第一天动作清单(按序,半天内)

### 1. 安全底线(先于一切,详见 [`07-backup-secrets.md`](./07-backup-secrets.md))

- [ ] 密钥红线立死:密钥文件位进 `.gitignore`;**从第一行代码起"密钥永不入仓库"**。
  ⚠️ 《密钥总备份》清单**不**第 0 天建(零密钥项目不建空账)——**首个密钥引入当天**再建档
- [ ] 建异地备份 remote(私有仓库,SSH 公钥认证),推第一笔,验证能拉回。
  **owner 不在场/建不成** → 挂"要 owner 亲手做的:建备份库"(handoff §三)+ 主文档标警示
  "建立之前仓库只有本地一份";建好当天补首推+核 0
- [ ] 备份说明写在**主仓** `备份/README.md`(装得下/装不下清单+恢复步骤),建 remote 那天写

### 2. 主文档 AGENTS.md

- [ ] 复制 [`templates/AGENTS.md`](./templates/AGENTS.md) 到仓库根,填【项目自填】区
  (红线表、路由表的项目行)。**它只装灵魂和路由,细则住各自的文档。**

### 3. 开发环境记录(最容易漏、最常被问的一件事)

- [ ] 建 `architecture.md`(复制 [`templates/architecture.md`](./templates/architecture.md)),
  **第一件填实的就是 §0「开发环境与跑法」**,内容清单:

| 记什么 | 例 |
|---|---|
| 解释器与路径 | Python 3.11(conda env `pywork`)/ Node 20 |
| 包管理器与安装命令 | `pnpm install` / `uv sync`(后端独立 venv,别混) |
| 怎么启动 | `pnpm dev` / 双击 `run.bat` |
| 怎么跑测试 | `pnpm test`(哪些档、各多久) |
| 平台已知坑 | 中文 `.ps1` 必须 UTF-8 带 BOM;路径带空格要加引号 |
| 别碰的东西 | 别临时 pip install 污染系统 Python;密钥文件别读 |

**判据:一个新会话的 agent 只读这一节,不问任何人就能把项目跑起来。**
AGENTS.md 里只留一行指针("环境与跑法 → architecture.md §0"),不抄第二份。

### 4. 需求源与空账

- [ ] `demand.txt`:owner 的原始需求**原话**贴进去(不加工、不总结)——它是唯一权威需求源
- [ ] 三份空账起步:`docs/handoff.md`、`docs/lessons.md`、`docs/history/INDEX.md`
- [ ] `.gitignore` 头部写判据:"跑批产物能不能由已入库的东西+一条确定性命令重新生成?
  能→ignore;不能(花过钱/唯一物证)→入库"
- [ ] 第一笔 commit("做了什么+为什么")→ 推备份 → 核 count=0

## 二、总需求讨论(阶段 1 的正事)

**目标**:把 demand.txt 细化成两份文档——`spec.md`(产品做什么)+ `architecture.md`(技术怎么做)。
**这一步不许跳**:没有它们,后面 roadmap 无从拆、SPEC 无从写、测试无从验。

### 讨论怎么做(对 owner,不对空气)

1. **先复述**:用自己的话把 demand.txt 讲一遍给 owner 听("我理解这个产品是……对吗?")——
   复述不出来 = 还没听懂,回去再问。
2. **问方向性的问题,不问细节**:3-5 个会让产品走不同路的(给谁用/核心场景/边界在哪/
   先做什么后做什么),每个带 2-3 个选项和取舍、标推荐。配色文案这类细节不问,取默认。
3. **有行业标杆必须对照**:成熟工具里已有公认实现 → 描述标杆的做法,让 owner 拍
   "跟谁一样 vs 不一样在哪"。**闭门设计再让他审,他没法判断方案值不值。**
4. **拿不准的技术路线 → 先做最小实验**:效果说不准的关键环节(通常是 AI 行为/算法效果),
   用真实数据跑一个最小实验,**给他看具体输入+输出**——他看实验结果能判好坏,看方案文档判不了。

### 产出 1:`docs/spec.md`(产品规格)

写法要点(模板:[`templates/spec.md`](./templates/spec.md)):

- **只写"做什么",不写"怎么做"**(怎么做在 architecture)
- 必有:**一句话定位 → 目标用户(一张表)→ 使用流程(站在使用者视角,一步一步:
  用户在什么场景、做什么操作、看到什么)→ 功能清单**
- 功能清单每条后标注将来落地它的 SPEC 号(如 `(SPEC-003)`)——从规格到需求可回溯
- 它是"产品当前应有的样子"的**现状快照**:以后改了用户可见行为,回来同步这一节

### 产出 2:`architecture.md` 填实

写法要点(模板:[`templates/architecture.md`](./templates/architecture.md)):

- **核心决策表(D 编号)**:每行 = 决策项 / 选定方案 / **否决项与理由**。
  ⚠️ 否决项一栏是灵魂——三个月后有人问"为什么不用 X",答案就住这。
- **待决问题区**:摆上桌但 owner 说"以后再说"的方向性问题,记下"何时回来评估"——
  不是 bug 不是待办,是没被遗忘也没被拍死的取舍。
- **整体拓扑**(一张图)+ **代码地图**(目录树+各目录一句话+"改 X 功能去哪个文件")。
  代码地图随目录结构变化同步更新——**过时的地图比没有还坑人**。
- **修订记录**:每次架构决策变更记一行(谁拍的、推翻了什么)。
  **用户提了跟旧决策冲突的方向 → 先引用决策号指出冲突,真改了必须更新本表。**

两份都写完、owner 认可 → 进 [`02-dev-workflow.md`](./02-dev-workflow.md):拆解 roadmap、建 specs/、逐个过需求。
